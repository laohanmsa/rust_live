## 七项失败

| 测试 | 观察到的结果 | 对切换的影响 |
| --- | --- | --- |
| `compat_request_price` | 请求价格事件没有订阅，解码失败 | 旧应用所需事件不完整 |
| `compat_legacy_redis_delivery` | 测试消息服务正常，但旧消费者订阅的提案频道没有收到消息 | 尚无旧协议发布通道 |
| `legacy_bridge_has_required_event_data` | 三类事件合计缺 16 个字段位置，包括 requester、identifier、ancillary_data、到期时间、争议双方及 payout | 仅转发现有精简消息不足以还原旧事件 |
| `bad_primary_head_must_not_pin_healthy_backup` | 错误主节点返回错误末端哈希；备用节点收到 3 次请求却被判定 `chain changed during scan` | 一致的备用扫描仍被主节点的错误基准阻碍 |
| `silent_empty_responses_must_not_report_complete` | 连续三次返回空日志后，事件数为 0，备用请求为 0，仍报告就绪 | 当前就绪不能证明没有静默漏日志 |
| `long_gap_must_replay_events_older_than_trading_window` | 手动注入内存断点 100，区块 200 的事件已过去 24,000 秒；启动完成但没有重放它 | 四小时交易窗口不能代替全局历史恢复 |
| `unchanged_window_must_not_download_old_blocks_again` | 无变化窗口两次都接收 210,013 字节，历史区块读取次数由 1 增至 2 | 重复下载开销真实存在 |

后三类故障属于隔离环境下的替换要求，并不表示这几个故障刚刚在生产发生。
空响应测试要求独立完整性核查，这是比“请求成功”更强的目标。
开销测试要求在保留链上重组核验的前提下复用数据，不允许为了降低流量直接跳过一致性检查。

## 为什么入站流量相差约 37.5 倍

这是此前保留的同机 60.1099842 秒观测，本轮没有重新测量生产流量。

| 方向 | Rust | 旧版 |
| --- | ---: | ---: |
| 入站 | 34,150,604 字节 | 910,964 字节 |
| 出站 | 12,973,706 字节 | 323,002 字节 |

Rust 在稳定扫描中反复回看 64 个区块，为其中含事件的区块逐个调用 `eth_getBlockByNumber(..., false)`。
这个接口返回区块对象，交易详情关闭时仍包含交易哈希列表；不是只有哈希和时间戳的小型区块头，参见 [以太坊节点接口说明](https://ethereum.org/developers/docs/apis/json-rpc/#eth_getblockbynumber)。
稳定扫描每轮约有 `5 + B` 次节点调用，B 是窗口内含事件的不同区块数量；扫描结束后再等待两秒。
旧版主要依赖实时事件推送并按需补抓，调用模式不同。

本次合成场景让每个区块包含 1,000 个交易哈希，两条事件所在区块加末端核验共返回三个区块对象。
第一次和完全无变化的第二次扫描均下载 210,013 字节响应正文，直接复现了重复下载机制。
该数字不含网络协议及加密开销，也不能外推成生产 34.15 MB 的精确分解。
因此重复扫描是有代码和实验支持的重要来源；各接口究竟占生产流量多少，仍缺按方法记录的真实字节统计。

旁路每 30 秒读取一次全量事件快照，主要增加 UMA 的出站流量，与本次出站约 12.97 MB 的量级相符。
此前以 Python 默认序列化估出的单份约 6.6 MB 不是线上压缩或序列化后的精确传输大小。
流量、请求数、连接数和供应商计费额度是四种不同指标，不能互相直接换算。

## 尚未完成的完整替换验收

1. 真实采集进程在发布、落盘、更新断点前后崩溃，重启后从持久断点恢复。
2. 消息服务断网、重启、消费者离线和数据库暂时失败后的重放与幂等入库。
3. 长连接仍存活但不发消息、持续超时、连接背压和大规模消息缺口。
4. 真实争议及请求价格历史样本、全部旧事件字段的值和时间单位兼容验证。
5. 完整 24 小时同区块对账、历史高峰回放、延迟分位和按节点方法计量。

Core NATS（基础消息总线）和 Redis Pub/Sub（发布订阅）都不是持久离线消息队列。
参考 [NATS 交付语义](https://docs.nats.io/learn/core-nats/) 和 [Redis 交付语义](https://redis.io/docs/latest/develop/pubsub/)。
旧发布与断点原子写入也不等于旧消费者已经成功入库。
